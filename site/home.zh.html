工作原理

中间只有一次握手

两台设备只要知道怎么找到对方，就能直接通信。freedrop 只借公共 MQTT 服务器转交这段加密的“自我介绍”，之后就不再经过它。

  1. 选文件

    freedrop 为这次传输生成一个全新的 256 位密钥，并以三种形式给出：链接、二维码，和一行 npx freedrop <code> 命令。

  2. 碰头

    双方从密钥推导出同一个房间，经公共 MQTT 服务器交换几 KB 的 WebRTC 握手信息，全程 AES-256-GCM 加密。服务器只能看到一个随机话题上的密文。

  3. 传输

    NAT 打洞之后，文件经 WebRTC 数据通道从一台设备直达另一台，DTLS 端到端加密。速度取决于两台设备之间的网络路径。

你能得到什么

大文件也放心交给它

数据不经过服务器

字节从设备直达设备。文件不会停在服务器上等对方来取，也没有中转服务器替你付流量——或者看你的流量。

端到端加密

传输用 DTLS，握手用 AES-256-GCM。链接里的密钥放在 URL 的 # 后面，浏览器从不把这部分发给任何服务器，本站也收不到。

不限大小，无需注册

没有注册，没有配额，没有过期时间。唯一的限制是接收方的剩余空间。

断点续传

Wi-Fi 断了、合上了笔记本、进程被杀：重新运行命令或重新打开链接，只补传缺失的部分。

每个文件都校验

按 4 MiB 分块做 SHA-256，校验通过才以真实文件名出现。发送途中源文件被改动会明确报错，不会悄悄落下一个损坏的文件。

该快的地方够快

CLI 用原生 WebRTC：本机回环 CLI 对 CLI 约 430 MB/s。超过 64 MB 的传输拆到四条连接上并行，小文件一个接一个流水线发送。

扫码接收

手机对准发送方的二维码，传输直接在页面里打开。添加到主屏幕后，freedrop 会出现在 Android 的分享菜单里。

适合脚本和 Agent

没有终端时不弹提示、不刷屏，--json 把事件逐行输出到 stdout，退出码直接说明下一步该做什么。

给 AI Agent

让 Agent 直接把文件交给你

编程 Agent 跑在沙箱、容器和远程机器里——你的下载文件夹够不着的地方。有了 freedrop，Agent 运行一条命令、把链接交给你，等你收齐每个字节后自行退出。反过来也行：你在手机上选文件，Agent 来接收。

安全模型

谁能看到什么

每个链接和命令里的那串代码，就是这次传输专用的 256 位密钥。路上任何可能被看到的东西，都由它、或由它建立的 WebRTC 会话加密。

谁能看到什么
公共 MQTT 服务器几 KB 的 AES-256-GCM 密文，发在一个由密钥单向哈希得出的话题上
本站的托管方一次普通的页面加载。链接里的密钥在 # 后面，浏览器从不把这部分发给任何服务器
途经的网络DTLS 加密的 WebRTC 数据包
TURN 中继（仅当你自己加了）它负责转发、但解不开的数据包
拿到链接或代码的任何人这次传输本身——链接就是密钥，只发给接收方。一个链接只对应一次传输，传完发送方就离开

每个文件在读取时还会做哈希（按 4 MiB 分块 SHA-256），到达后先校验，通过才以真实文件名出现。

对比

freedrop、croc、magic-wormhole 及其他

区别在于：你的数据走哪条路，以及要有什么一直在线它才能工作。freedrop 让数据直连，自己不运营任何服务器——公共 MQTT 服务器只转交加密的“自我介绍”。

工具数据走向依赖的服务器浏览器 ⇄ 终端
freedrop点对点直连（WebRTC）公共 MQTT 服务器，仅用于握手都支持，任意组合
crocNAT 穿透成功时直连；否则（以及浏览器一端）经中继公共中继（getcroc.com）都支持（网页端 getcroc.com）
magic-wormhole直连，或经 transit 中继mailbox 服务器和 transit 中继终端；另有第三方网页客户端
webwormhole点对点（WebRTC）信令服务器都支持
FilePizza、PairDrop点对点（WebRTC）Tracker 或自有信令仅浏览器
网盘式上传链接（WeTransfer 等）先上传、存储，再下载服务商的存储浏览器

其他工具做得更好的地方

  • croc 和 magic-wormhole 有中继兜底，两端都在对称型 NAT 后面也能连上；freedrop 需要你用 --turn 指定一个 TURN 中继。
  • 它们的短口令可以电话里念给对方；freedrop 的代码很长，只能复制、点链接或扫码。
  • croc 能直接发文件夹；用 freedrop 请先用 tar 打包。

设计上的限制

  • 两端必须同时在线——中间不存任何东西。
  • MQTT 服务器在互联网上，所以离线局域网里的两台机器暂时找不到彼此。
  • 浏览器作为发送方时，刷新页面后无法续传（选好的文件不会保留）；浏览器接收方和 CLI 都能续传。

计划中：短口令、文件夹、局域网发现。

常见问题

大家常问的

还有疑问？README 讲得更细，也欢迎提 issue。

freedrop 免费吗？

免费。freedrop 以 MIT 协议开源。数据不经过中继，也就没有流量费用要转嫁给你：没有套餐，没有广告，不用注册。

文件大小有限制吗？

没有。文件直接写到接收方，上限就是那边的剩余空间。用浏览器接收时，还受浏览器分配给网页的存储空间限制。

别人能看到我的文件吗？

没有任何服务器经手你的文件。MQTT 服务器只转交加密的握手信息，文件经 DTLS 加密直达接收方。不过链接或代码本身就是密钥：拿到它的人都能接收，所以只发给接收方。

需要安装什么吗？

用浏览器不需要：在任意设备上打开 freedrop.dev 即可。终端里运行 npx freedrop，需要 Node.js 22 及以上，无需配置。网页也可以添加为应用，添加后 freedrop 会出现在 Android 的分享菜单里。

两台设备必须同时在线吗？

是的。中间不存储任何东西，所以在接收方收齐之前，请保持发送页面或命令运行。

传到一半断了怎么办？

会续传。网络抖动后两端自动重连；进程崩溃或关掉了标签页，重新运行同一条命令或重新打开同一个链接，只补传缺失的部分。唯一的例外：浏览器发送方刷新页面后，需要重新选择文件。

国内能用吗？在 NAT 和防火墙后面呢？

通常可以。NAT 打洞能覆盖大多数家庭和移动网络，默认配置里也包含中国大陆可以直连的 STUN 服务器和 MQTT 服务器。如果两端都在对称型 NAT 或运营商级 NAT（CGNAT）后面，可以用 --turn 加一个 TURN 中继（Cloudflare 的免费额度，或自建 coturn），中继只转发它解不开的数据包。

和 AirDrop、网盘、聊天软件传文件有什么不同？

AirDrop 要求两台苹果设备就在附近；网盘和聊天软件要先把文件上传到它们的服务器。freedrop 在任意两台联网设备之间直接传，文件不会存到任何地方；代价是两端必须同时在线。

AI Agent 能用 freedrop 吗？

能。没有终端时它只输出纯文本行；加 --json 后在 stdout 上逐行输出事件；退出码告诉 Agent 下一步该怎么做。完整说明见 https://freedrop.dev/llms.txt。

能发文件夹吗？

暂时不能直接发。先打包（tar czf photos.tgz photos），再发送压缩包。
