# freedrop 的工作原理

freedrop 通过两台设备之间直连的 WebRTC 连接传文件，用 DTLS 端到端加密。唯一经过别人服务器的，是几 KB 的握手信息，用 AES-256-GCM 加密；密钥是 256 位、每次传输重新生成，只存在于你分享出去的链接或命令里。没有任何服务器存储、中转或能读取你的文件。

## 代码就是密钥

每次传输都从一个新的随机 256 位密钥开始。`npx freedrop <code>` 里的代码、链接 `https://freedrop.dev/r/#<code>` 里的代码、二维码里的代码，都是这个密钥的 base64url 编码。其他一切都由它派生：碰头用的房间，以及房间里每条消息的加密。

## 碰头：经公共 MQTT 服务器交换握手

两台在家用路由器后面的设备，没法直接呼叫对方。它们得先交换地址和连接参数——WebRTC 的 SDP 和 ICE 候选，总共几 KB。freedrop 借公共 MQTT 服务器完成这一步：EMQX（国际和中国大陆各一个入口）和 HiveMQ。

1. 两端用单向哈希从密钥推导出房间 ID，所以碰头用的话题不会泄露任何关于密钥的信息。
2. 房间里的每条消息都用这个密钥做 AES-256-GCM 加密。服务器只能看到一个随机话题上的密文，别的什么都看不到。
3. 两端直连之后，文件就不再经过 MQTT 服务器。只有需要重连时才会再用到这个房间。

不需要托管任何东西：没有 freedrop 服务器，没有账号，也没有自己的信令服务。想用自己的 MQTT 服务器，用 `--broker` 让两端改连别的 `wss://` 地址即可。

## 连接：WebRTC、DTLS 和 NAT 打洞

两端各自向 STUN 服务器（Cloudflare、Google，以及一个中国大陆可以直连的服务器）询问自己的公网地址，再穿过各自的 NAT 直接连上对方。之后文件经 WebRTC 数据通道传输，DTLS 端到端加密。线路上的完整性由 DTLS 和 SCTP 保证，路径上也没有能篡改数据的中继。

超过 64 MB 的传输在两端都支持时会拆到四条连接上并行，每条都同样加密。每个数据帧都带着自己的偏移量，所以行为异常的 WebRTC 实现会被发现，而不是被盲目信任：重复的帧丢弃，出现缺口直接报错。

## 密钥不会到达任何服务器

在浏览器链接里，密钥放在 URL 的片段（`#` 后面的部分）里。浏览器从不把片段发给任何服务器，所以网页的托管方——freedrop.dev，或者任何托管这个静态页面的地方——只看到一次普通的页面加载，拿不到密钥。页面背后也没有能记录任何东西的后端。

## 谁能看到什么

| 谁 | 能看到什么 |
|---|---|
| 公共 MQTT 服务器 | 几 KB 的 AES-256-GCM 密文，发在一个由密钥单向哈希得出的话题上；和任何互联网服务一样，还有你的 IP 地址 |
| STUN 服务器 | 一次询问公网地址的请求，来自你的 IP 地址 |
| 网页的托管方 | 一次普通的页面加载；片段里的密钥不会发过去 |
| 途经的网络 | DTLS 加密的 WebRTC 数据包 |
| TURN 中继（仅当你自己加了） | 它负责转发、但解不开的数据包 |
| 对端 | 你的文件，以及你的 IP 地址——直连本来就意味着这一点 |
| 拿到链接或代码的任何人 | 这次传输本身——链接就是密钥 |

## 完整性：每个字节都校验

- 发送方边读文件边算哈希：按 4 MiB 分块做 SHA-256。
- 接收方先写入暂存区里的 `<name>.part`，再重新读取暂存的数据比对哈希，通过后才改名为真实文件名。
- 源文件在两次尝试之间被改动的话，会明确报错（退出码 5），而不是悄悄落下一个损坏的文件；修改时间一变，旧的部分数据会提前作废。重新运行会把这个文件完整重传。
- 在浏览器里，同样的校验在文件变成可下载之前完成。

## 断点续传

接收方在暂存数据旁边保存一个小日志，记录已经落盘的字节区间。任何一次重连都只补传缺失的部分。传输可能断掉的每一种情况都覆盖到了：

- **首次连接**：约 5 秒没有信令进展，就重新握手，连接窗口约 15 秒，不用刷新页面。
- **网络抖动**：两端都还在运行，经碰头房间重新协商后继续。接收方会持续重试约 90 秒，日志无论如何都会保留。
- **接收方挂了**：重新运行同一条 `npx freedrop <code>`，或重新打开同一个链接——浏览器里的暂存区在标签页关掉后依然保留。
- **发送方挂了**：用 `freedrop --code <code> <files>` 重新运行，还在等待的接收方会自动重连。

唯一的例外是浏览器**发送方**：网页里选好的文件在刷新后不会保留，所以刷新后无法续传。浏览器接收方和 CLI 的收发两端都能续传。

## NAT 与 TURN

NAT 打洞能覆盖大多数家庭和移动网络。唯一打不通的组合，是两端都在对称型 NAT 或运营商级 NAT（CGNAT）后面。这时发送方可以用 `--turn` 指定一个 TURN 中继：Cloudflare 的（每月 1 TB 免费），或者自建的 coturn。中继只转发它解不开的数据包，传输仍然端到端加密。

freedrop 故意不内置中继兜底。正因如此它没有流量费用要转嫁给你，也没有谁的服务器会经手你的数据。代价是：两端都在对称型 NAT 后面时，需要你自己选一个中继、多加一个参数——具体命令见[命令行](/zh/cli/)一页。

## freedrop 防不了什么

- **拿到链接或代码的人都能接收。** 只通过你信任的渠道发给接收方。
- **一个链接只对应一次传输。** 传完发送方就离开了；在接收的浏览器里重新打开链接，只会显示已经收到的文件，不会有新内容。
- **两端必须同时在线。** 中间不存任何东西，这是设计使然。
- **由接收方决定收不收。** CLI 会先列出文件、问过才保存（`-y` 跳过确认）；浏览器里在接收方点「保存」之前什么都不会存。接收方拒绝时，CLI 发送方以退出码 6 退出。
- **两端能看到彼此的 IP 地址**，任何直连都是如此。
