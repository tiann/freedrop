How it works

The only thing in the middle is a handshake

Two devices can talk directly once they know how to reach each other. freedrop uses public MQTT brokers only to pass that introduction along, encrypted, and then gets out of the way.

  1. Pick files

    freedrop makes a fresh 256-bit key for this transfer and shows it three ways: a link, a QR code and an npx freedrop <code> command.

  2. Meet

    Both ends derive a room from the key and swap a few kilobytes of WebRTC handshake through public MQTT brokers, sealed with AES-256-GCM. The brokers see ciphertext on a random-looking topic.

  3. Transfer

    The files flow over a WebRTC data channel, straight from one device to the other after NAT hole-punching, DTLS-encrypted end to end. Speed is whatever the path between them allows.

What you get

Built to be trusted with big files

No server in the data path

Bytes go device to device. Nothing waits on a server for the other side, and no relay pays for — or reads — your traffic.

End-to-end encrypted

DTLS on the wire, AES-256-GCM for the handshake. In a link the key rides the URL fragment, which browsers never send to any server — this site's included.

No size limit, no account

No sign-up, no quota, no expiry timer. The only limit is free space on the receiving side.

Resumes where it stopped

Wi-Fi dropped, laptop closed, process killed: re-run the command or reopen the link, and only the missing byte ranges travel.

Every file verified

SHA-256 over 4 MiB blocks, checked before a file appears under its real name. A source that changed mid-way fails loudly instead of landing corrupt.

Fast where it counts

Native WebRTC in the CLI: about 430 MB/s CLI to CLI on loopback. Transfers over 64 MB stripe across four connections; small files pipeline back to back.

Scan to receive

Point a phone at the sender's QR code and the transfer opens in place. Added to the home screen, freedrop joins Android's share sheet.

Made for scripts and agents

No prompts or redraws without a terminal, --json events on stdout, and exit codes that say what to do next.

For AI agents

Let your agent hand you a file

Coding agents work in sandboxes, containers and remote machines — places your downloads folder can't reach. With freedrop the agent runs one command, gives you a link, and exits once you have every byte. It works the other way too: pick files on your phone, and the agent receives them.

  • No terminal, no prompts. Plain lines, no QR code, no redraws; a receiver without -y exits instead of waiting for an answer.
  • One JSON event per line with --json: ready, progress, saved, done, error.
  • Exit codes that say what to do next — 8: re-run to resume, 4: retry with a TURN relay, 7: timed out.
  • A guide written for agents at freedrop.dev/llms.txt.

Security model

Who sees what

The code in every link and command is a 256-bit key, made fresh for each transfer. Everything that could be observed along the way is encrypted with it, or with the WebRTC session it sets up.

WhoWhat they see
Public MQTT brokersA few KB of AES-256-GCM ciphertext, on a topic derived from the key by a one-way hash
The host of this pageAn ordinary page load. In a link the key sits after the #, and browsers never send that part to any server
Networks in betweenDTLS-encrypted WebRTC packets
A TURN relay, if you add onePackets it forwards but cannot decrypt
Anyone holding the link or codeThe transfer — the link is the key, so share it with the recipient only. A link carries one transfer: the sender leaves once it's done

Every file is also hashed as it is read (SHA-256 over 4 MiB blocks) and checked on arrival, before it appears under its real name.

Compared

freedrop, croc, magic-wormhole and the rest

The difference is where your bytes go and what has to keep running for it to work. freedrop keeps the data path direct and runs no servers of its own — the public brokers carry only the encrypted introduction.

ToolWhere the data goesServers it relies onBrowser ⇄ terminal
freedropDirect, peer-to-peer (WebRTC)Public MQTT brokers, for the handshake onlyBoth, in any mix
crocDirect when NAT traversal works; otherwise, and for browser peers, through a relayPublic relays (getcroc.com)Both (web client at getcroc.com)
magic-wormholeDirect, or through a transit relayA mailbox server and a transit relayTerminal; third-party web clients
webwormholePeer-to-peer (WebRTC)A signaling serverBoth
FilePizza, PairDropPeer-to-peer (WebRTC)Trackers or their own signalingBrowser only
Upload links (WeTransfer-style)Uploaded, stored, then downloadedThe provider's storageBrowser

What the others still do better

  • croc and magic-wormhole fall back to a relay, so they connect even when both ends sit behind symmetric NAT. freedrop needs a TURN relay you name with --turn.
  • Their short codes can be read out over the phone. freedrop's code is long: copy it, open the link or scan the QR code.
  • croc sends folders. With freedrop, tar them first.

Limits by design

  • Both ends must be online at the same time — nothing is stored anywhere in between.
  • The brokers are on the internet, so two machines on an offline LAN can't find each other yet.
  • A browser sender can't resume after a page reload: the picked files don't survive it. Browser receivers and the CLI both resume.

On the roadmap: short codes, folders, local-network discovery.

FAQ

Questions people ask

Anything else: the README goes deeper, and issues are open.

Is freedrop free?

Yes. freedrop is MIT-licensed open source. With no relay in the data path there is no traffic bill to pass on: no plans, no ads, no account.

Is there a file size limit?

No. Files go straight to the receiver, so the limit is the free space there. A receiving browser is also bound by how much storage it lets the page use.

Can anyone else see my files?

No server ever holds them. The brokers carry only an encrypted handshake, and the files travel DTLS-encrypted straight to the receiver. The link or code is the key, though: anyone who has it can receive, so send it only to the recipient.

Do I need to install anything?

Not in a browser: open freedrop.dev on any device. In a terminal, npx freedrop runs it with Node.js 22 or newer, with nothing to configure. The page can also be added as an app, which puts freedrop in Android's share sheet.

Do both devices have to be online at the same time?

Yes. Nothing is stored in between, so keep the sending page or command running until the receiver has every byte.

What if the connection drops halfway?

It resumes. After a network blip both ends reconnect on their own; after a crash or a closed tab, re-run the same command or reopen the same link and only the missing parts travel. The one exception: a browser sender that reloads has to pick the files again.

Does it work behind NAT, firewalls, or in mainland China?

Usually, yes. NAT hole-punching covers most home and mobile networks, and the defaults include STUN and broker servers reachable from mainland China. When both ends are behind symmetric or carrier-grade NAT, pass a TURN relay with --turn (Cloudflare's free tier, or your own coturn); it forwards packets it cannot read.

How is freedrop different from AirDrop or WeTransfer?

AirDrop needs Apple devices near each other. Upload services store your file on their servers first. freedrop works between any two devices over the internet and never stores the file anywhere; the trade-off is that both ends must be online together.

Can an AI agent use freedrop?

Yes. Without a terminal it prints plain lines, --json gives one event per line on stdout, and exit codes tell the agent what to do next. The full guide is at https://freedrop.dev/llms.txt.

Can I send a folder?

Not directly yet. Archive it first (tar czf photos.tgz photos) and send the archive.
